# Give Me Solutions

Return decision material, not a vendor list and not a decision made on the user's behalf.

1. Establish the real job, system boundary, constraints, existing owned assets, and disqualifiers. If the failing responsibility is still unclear, use `zoom-out` before researching products.
2. Test whether an existing asset can perform the bounded role before adding another product. Reuse is a candidate, not an automatic winner.
3. Search the viable candidate field in one bounded pass. Keep a source ledger for each candidate: official capability and terms, dated independent reviews, long-term user reports, failure stories, and real operating evidence.
4. Reject candidates that fail a hard requirement. Compare every survivor against the same requirement set, including setup cost, recurring cost, migration, lock-in, reliability, security, and operating burden.
5. Stop when the relevant candidate classes are covered, hard unknowns are explicit, and another search pass is no longer changing the ranking or revealing a new failure class.
6. Present the strongest options first. For each, show why it fits, advantages, disadvantages, hidden cost, operational risk, evidence freshness, and who it suits.
7. Name the current front-runner when evidence supports one, but preserve meaningful alternatives and leave the final choice to the user.

Mark vendor claims, independently confirmed facts, inference, unknowns, and stale evidence. Popularity and polished demos are not outcome proof. Do not compare a whole platform against one narrow component or invent a place for every mentioned tool.
